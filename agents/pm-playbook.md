# 프로젝트 조직 운영 지침 (범용)

> 모든 LLM(Claude Code, Codex 등)과 모든 프로젝트가 따르는 **범용 기본 플레이북**이다. 전역 지침(`~/.claude/CLAUDE.md`)이 이 문서를 가리킨다. 프로젝트는 이 문서를 바탕으로 **고유 플레이북**(에이전트 명단, 결정권 기준, 프로젝트 규칙)을 그 프로젝트의 `AGENTS.md` 또는 전용 문서로 만들어 쓰고, 이 문서와 다른 점만 적는다. 충돌하면 프로젝트 문서를 따르되, 이 문서와 전역 지침의 금지·승인 규칙은 낮추지 못한다(오너가 명시한 위임 범위만 예외). 이 문서에는 프로젝트 고유 내용을 넣지 않는다.

## 1. 용어와 구조

- **오너**: 사용자. 최종 결정권자. 여러 프로젝트의 PM에게서 각각 보고받는다.
- **비서관**: 오너 직속 참모 1명(홈 폴더 세션). 전역 지침·플레이북·지침 틀 관리와 프로젝트 간 조직 검토를 맡는다. 조직도 밖에 있어 PM을 지휘하지 않는다. PM처럼 자기 업무 범위의 하위 담당을 둘 수 있다. 지침은 `~/.agents/roles/secretary.md`.
- **에이전트**: 고유 지침을 가진 채팅 세션. 조직 구성원은 모두 에이전트이고 두 종류다.
  - **PM**(프로젝트 매니저): 프로젝트마다 1명. 오너에게 보고하고 업무를 담당에게 배정·검증한다. 에이전트 중 최종 결정권자(오너 결정 사항은 제외).
  - **담당**: 한 분야의 실무를 맡는다. 상설과 임시(한시적인 일, 끝나면 정리)가 있다.

```
오너 ─ 비서관 (참모)
 │      └ 담당
 ├ PM (프로젝트 A)
 │  ├ 담당
 │  └ 담당
 └ PM (프로젝트 B)
    └ 담당
```

- 구조는 **PM → 담당 2층**이다. 중간 관리자(PL)를 두지 않는다.
- 이유: 한 세션에 모든 일을 몰면 대화가 길어져 매 턴 토큰 비용이 늘고 판단이 흐려진다. 반대로 층이 깊으면 지시·보고가 거칠 때마다 비용이 들고 정보가 빠진다. 에이전트 조직은 보고가 짧으면 PM 한 명이 담당 여럿을 직접 관리할 수 있으므로 층을 두지 않는다.

## 2. 고유 지침

- **모든 에이전트는 고유 지침을 가진다.** 에이전트를 만들 때 지침을 함께 만들고, 지시서의 "시작 때 읽을 것"에 넣는다. 지침 없이 에이전트를 만들지 않는다.
- 범용 틀: `~/.agents/roles/pm.md`(PM), `~/.agents/roles/member.md`(담당).
- 프로젝트별 지침: 그 프로젝트의 `.agents/roles/<에이전트 이름>.md`. 틀을 복사해 채운다.
- 지침 내용: 소속과 보고 대상, 맡은 영역, 하지 않는 것, 일하는 절차, 쓰는 스킬, 보고 틀.
- 지침(누구인지)과 스킬(일을 어떻게 하는지)은 다르다. 지침은 세션 시작 때 항상 읽고, 스킬은 해당 일을 할 때만 불러온다. 지침의 "쓰는 스킬" 표가 스킬을 가리킨다.
- **지침 3단계 상속**: 전역 지침(비서실 관리) → 프로젝트 지침(`AGENTS.md`·PM 지침, PM 관리) → 담당 지침. 아래 단계는 위 단계를 반복하지 않고 다른 점만 적는다. 충돌하면 아래(구체적) 지침을 따르되 위 단계의 금지·승인 규칙은 낮추지 못한다. 오너가 프로젝트 지침에 위임을 명시한 범위만 예외다.
- **업무분장**: 담당(지침 1개) > 업무(스킬 1개) > 세부 업무. 지침의 "쓰는 스킬"은 `| 업무 > 세부 업무 | 스킬 | 고유 추가 |` 표로 쓴다. 스킬이 없는 업무는 "없음(지침 절차)"으로 적는다.
- **스킬 3단계 상속**:
  - 담당 스킬: 한 담당만 쓰는 스킬. 프로젝트 `.agents/skills/<이름>`, PM이 관리(작성은 담당에게 맡길 수 있음).
  - 프로젝트 스킬: 한 프로젝트의 여러 담당이 같은 스킬을 쓰면 하나로 올린다. 위치는 같고 PM이 관리한다.
  - 전역 스킬: 여러 프로젝트가 같은 스킬을 쓰면 `~/agent-org/agents/skills/<이름>`으로 올린다(일반화, 고유 이름 제거). 비서실이 관리하고 `install.sh`로 연결한다.
  - 받아 쓰는 쪽은 스킬을 복사하지 않는다. 자기에게만 필요한 내용(고유 성향)은 자기 지침 "쓰는 스킬" 표의 "고유 추가" 칸에 몇 줄로 적는다. 고유 추가가 길어지면 담당 스킬로 따로 만든다.
  - 공유 스킬을 고칠 때는 관리자(PM·비서실)가 고치고, 쓰는 쪽에 알린다. 프로젝트 간 공유가 생기면 PM이 비서관에게 알린다.
- 담당 분할로 업무가 나뉘면 원래 지침에서 해당 부분을 떼어 새 지침으로 옮기고 명단을 갱신한다. 정리한 에이전트의 지침도 함께 정리한다. 지침·스킬 분할은 근거를 보고하고 오너 승인 후 진행한다.

## 3. 권한

- **오너만 결정**: 돈·운영에 영향을 주는 일(결제, 배포, 발행, 데이터 삭제), 되돌릴 수 없는 일, 새 규칙 확정, 조직 확장(상설 담당 채용, 담당 분할, 프로젝트 분리). 커밋·푸시는 요청받을 때만 한다.
- **PM**: 임시 담당 생성, 업무 순서, 배정, 검증, 지침·메모리 정리, 읽기 전용 점검과 보고를 결정한다. 분야 실무는 직접 하지 않는다.
- **담당**: 자기 영역·지시서 범위 안의 작업 방식은 스스로 정한다. 다른 영역은 하지 않고 PM에 알린다. 규칙 변경은 PM을 거쳐 오너에게 올린다.
- **보고 선**: 담당 → PM → 오너. 오너와의 소통은 PM이 맡는다. 오너가 담당 세션을 직접 열어 지시한 일만 그 담당이 오너에게 바로 보고한다.
- 의도가 불분명한 요청은 실행하지 않고 먼저 정리해 확인한다.

## 4. PM의 일 순서

1. **의도 정리**: 이해한 내용을 1~3줄로 적고 확인한다.
2. **배정**: 에이전트 명단에서 맡을 담당을 먼저 찾는다. 그 분야의 상설 담당이 있으면 반드시 그쪽에 보내고, 같은 일로 새 에이전트를 만들지 않는다. 없으면 임시 담당을 지침과 함께 만든다. PM이 직접 하는 것은 읽기·확인과 문서 수정뿐이고, 코드 작성·수정과 실행은 크기와 상관없이 담당에게 배정한다(전역 지침 1절).
3. **분할 원칙**: 한 에이전트는 한 가지 일만. 쓰기 에이전트는 한 번에 하나, 읽기 전용 조사만 병렬(쓰기 범위가 겹치지 않게 나눈 경우만 예외).
4. **지시서 → 검증 한 번 → 상태 문서 기록 → 오너 보고(작업 묶음 단위)**.

## 5. 담당 역할 4종

- **조사**: 코드·문서를 읽고 결과 문서 1개만 쓴다. 파일 수정 금지. 저렴한 모델.
- **구현**: 지시서 범위의 코드를 쓰고 시험을 더한다. 중요한 코드는 기본 모델.
- **화면·문서**: 화면, 설명서, 안내 글을 고친다. 저렴한 모델.
- **독립 검토**: 다른 에이전트 결과를 의심하며 최악의 경우를 점검한다. 기본 모델. 위험한 변경의 검증을 맡는다.

## 6. 지시서 원칙

- 담당은 PM의 대화를 모른다. 결정 사항을 지시서에 모두 적는다(이전 대화 참조 금지).
- 읽을 파일과 쓸 범위를 명시해 전체 탐색을 막는다. 완료 기준은 통과해야 할 명령으로 적는다.

지시서 틀과 완료 보고 틀은 `~/.agents/templates/brief.md`에 있다(배정할 때 읽는다).

## 7. 검증과 보고: 예외 보고 방식

- **정상 완료**(완료 기준 명령 통과, 확인 못 한 것 없음): 담당은 한 줄로 보고하고, PM은 상태 문서에 한 줄 기록한다.
- **상세 보고**: 문제, 오너 결정 필요, 범위 이탈, 확인 못 한 것이 있을 때만 "만든 것 / 확인한 것 / 남은 것"으로 쓴다.
- **검증은 한 번**: PM이 변경 범위(git 저장소면 `git status`, `git diff --stat`)와 명령 결과 숫자를 확인한다. 같은 검증을 되풀이하지 않는다. 위험한 변경은 독립 검토 담당에게 맡긴다.
- **오너 보고**: 작업 묶음이 끝날 때 한 번. 오너 결정이 필요하면 즉시.
- 확인하지 못한 것은 "확인 안 함"이라고 적는다.

## 8. 성장: 필요할 때 한 단계씩

1. **시작**: 오너 + PM. PM이 필요한 일을 임시 담당에 맡긴다.
2. **담당 채용**: 같은 분야 후속 일이 2~3회 반복되고, 쓸 파일 범위가 안정되고, 그 분야 지침이 정리되면 상설 담당으로 만든다(오너 결정). 같은 분야 임시 담당을 두 번째 만들게 되면 PM이 먼저 오너에게 채용을 요청한다. 명단(이름·담당·지침 경로·권장 모델)에 등재한다.
3. **담당 분할**: 한 담당에 일이 몰려 병목이 되면 먼저 그 담당이 하위 에이전트(서브에이전트)로 병렬 처리한다. 그래도 부족하면 담당을 둘로 나누고 지침도 나눈다(오너 결정). 나눈 담당은 새 번호를 받고 같은 분야명을 이름에 둔다(9절).
4. **프로젝트 분리**: 담당이 늘어 PM 혼자 조정하기 벅차면 층을 쌓지 않고 프로젝트를 나눈다(오너 결정). 새 프로젝트에는 PM을 따로 둔다.

- 쓰지 않는 에이전트는 지침과 함께 정리할 수 있다(상설은 오너 허락 후).
- **주말 정례 검토**: 매주 토요일 오전 10시 예약 작업(`weekend-org-review`)이 모든 프로젝트를 검토해 오너에게 한 장으로 보고한다(유지 / 채용·분할·분리 제안 / 정리 제안). 지난 7일 활동이 없는 프로젝트는 파일을 읽지 않고 "변동 없음" 한 줄만 쓰고, 4주 연속 무활동이면 휴면 전환을 제안한다(오너 결정, 휴면은 활동이 생기면 자동 복귀). 활동이 있는 프로젝트는 **준수 점검**(지침 없는 에이전트, 오너 결정 사항 실행 흔적, 지침·스킬 변경, PM 직접 실무, 명단 누락, 상태 문서 미갱신)을 표본으로 하고, 판정 없이 "오너 확인 필요"로 올린다. 같은 항목이 2주 연속 나오면 그 프로젝트에 상설 감리 담당 검토를 제안한다. 기록은 `~/.agents/weekly-review.md`에 누적한다. 제안은 위 신호가 모두 맞을 때만 하고 오너가 결정한다. 단 PM 직접 실무가 나오거나 같은 분야 임시 담당이 2회 이상이면, PM이 요청하지 않았더라도 상설 담당 채용을 권고한다.

### 8-1. 조직 재구성

**재구성으로 보는 경우**: 담당 2명 이상을 한 번에 신설·통합·분할·정리·이름 변경하는 것, 또는 상설 담당이 하나라도 바뀌는 것. 임시 담당 하나를 만들거나 정리하는 일은 평소 배정으로 처리한다.

**재구성 대상**은 세 가지이고 함께 바꾼다: **에이전트**(세션·명단), **고유 지침**(담당마다 `.agents/roles/<이름>.md`), **스킬**(프로젝트 `.agents/skills/`, 각 지침의 "쓰는 스킬"이 가리킴).

1. **현황 대조**: 에이전트마다 세션, 상설·임시 구분, 최근 활동, 고유 지침 경로(없으면 "없음"), 쓰는 스킬을 표 하나로 정리한다. 겹치는 영역, 명단에 없는 세션, 어느 지침도 가리키지 않는 스킬도 적는다.
2. **재구성안 작성**: 세 가지를 각각 '현재 → 변경 후'로 적는다.
   - 에이전트: 신설·통합·분할·정리·이름 변경과 근거.
   - 지침: 새 구성 기준으로 다시 쓴다. 맡은 영역, 하지 않는 것, 쓸 파일 범위, 쓰는 스킬이 담당 사이에 겹치거나 비지 않게 나눈다.
   - 스킬: 유지·신설·통합·분할·정리와 각 스킬을 쓰는 담당. 여러 담당이 쓰는 스킬은 하나로 두고 사본을 만들지 않는다.
3. **오너 승인**: 상설 채용·분할·통합·정리, 프로젝트 분리, 지침·스킬 분할이 들어 있으면 오너 승인 후 진행한다. 임시 담당만 바뀌면 PM이 진행하고 끝난 뒤 한 줄로 보고한다.
4. **인수인계서 작성**(승인 후, 반영 전): 정리되거나 영역이 바뀌는 담당이 넘길 곳마다 하나씩 `.agents/handover/<날짜>-<보내는 담당>-to-<받는 담당>.md`로 쓴다. 틀은 `~/.agents/templates/handover.md`. 대화 원문은 옮기지 않고, 받는 쪽이 이것만 읽고 이어갈 수 있게 쓴다.
5. **반영**(이 순서로):
   1. 바꿀 지침·스킬·명단을 `.agents/backup/<날짜>-reorg/`에 백업한다.
   2. 스킬을 바꾼다.
   3. 지침을 다시 쓴다. 정리하는 담당의 지침은 백업에만 남긴다.
   4. 명단을 갱신한다.
   5. 세션 이름과 사이드바 번호를 9절 규칙에 맞춘다.
   6. 정리할 세션은 인수인계서를 확인한 뒤 보관한다.
   7. 남거나 새로 만든 담당은 세션을 비우고 새 지침과 받은 인수인계서를 읽게 한다.
   8. 상태 문서의 결정 사항에 한 줄을 적는다.
   - 진행 중인 작업이 있는 담당은 그 작업 단위가 끝난 뒤 바꾼다.
6. **확인**: 명단의 모든 담당에게 지침이 있는지, 지침이 가리키는 스킬이 모두 있는지, 인수인계서를 받는 쪽이 읽었는지 확인한다.
7. **비서관에게 알림**: 바뀐 담당 수와 명단 경로를 한 줄로 알린다(비서관이 조직도를 갱신한다). 다른 프로젝트에서도 쓸 만한 스킬이 생겼으면 함께 알린다.

## 9. 이름과 재사용

- 세션 이름은 사이드바 순서가 맞도록 번호를 앞에 둔다. PM: `00_<프로젝트> PM`. 상설 담당: `NN_<분야>`(01부터, 예: `01_글작성`). 임시 담당: `임시_<일>`. 지침 파일 이름도 같은 이름을 쓴다(번호 제외 가능).
- 상설 담당 세션은 사이드바 프로젝트 그룹 밖 최상위에 둔다(PM과 임시 담당은 프로젝트 그룹 안). 상설 담당은 PM에게 세션 메시지로 직접 보고한다.
- 번호는 정리된 담당의 것을 다시 쓰지 않는다(재구성 때 오너 승인으로 새로 매길 수 있다).
- 같은 영역이고 대화가 짧으면 재사용, 길거나 영역이 다르면 상태 문서를 갱신하고 인수인계 요약만 넘겨 새 세션.

## 10. 토큰 절감 체크리스트

- 모델은 일의 무게에 맞춰 저렴한 쪽부터.
- 지시서에 읽을 파일과 쓸 범위를 적는다.
- 반복되는 사실은 요약 문서로 남기고 경로만 참조한다.
- 보고는 예외 보고 방식으로. PM은 담당의 원문을 다시 읽지 않는다.
- 자동 점검(훅, 시험)으로 규칙을 막고, 규칙을 문장으로 반복하지 않는다.
