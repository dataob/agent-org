# 코딩 원칙

> LLM이 코딩에서 자주 하는 실수를 줄이기 위한 지침이다. 코드를 작성·수정하는 모든 에이전트(주로 담당, 사소한 일을 직접 하는 PM 포함)가 작업 전에 읽는다. 전역 지침(`~/.claude/CLAUDE.md`)이 이 문서를 가리킨다. 프로젝트 지침과 함께 적용한다.

**균형:** 이 지침은 속도보다 신중함을 우선한다. 사소한 일은 판단껏 처리한다.

## 1. 코딩 전에 생각하기

**짐작하지 않는다. 헷갈리는 점을 숨기지 않는다. 장단점을 드러낸다.**

구현 전에:
- 가정을 명시한다. 확실하지 않으면 묻는다.
- 해석이 여러 가지면 제시한다. 몰래 하나를 고르지 않는다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반대 의견을 낸다.
- 불분명하면 멈추고, 무엇이 헷갈리는지 말하고 묻는다.

## 2. 단순함 우선

**문제를 푸는 최소한의 코드만. 추측성 코드는 쓰지 않는다.**

- 요청하지 않은 기능은 넣지 않는다.
- 한 번만 쓰는 코드에 추상화를 만들지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 넣지 않는다.
- 일어날 수 없는 상황의 오류 처리를 넣지 않는다.
- 200줄로 쓴 것이 50줄로 될 수 있으면 다시 쓴다.

스스로 묻는다: "숙련된 개발자가 보면 과하다고 할까?" 그렇다면 단순하게 고친다.

## 3. 필요한 곳만 고치기

**고쳐야 할 곳만 건드린다. 내가 만든 흔적만 치운다.**

기존 코드를 고칠 때:
- 주변 코드·주석·서식을 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩터링하지 않는다.
- 내 취향과 달라도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 알리기만 하고 지우지 않는다.

내 변경으로 쓸모없어진 것이 생기면:
- 내 변경 때문에 안 쓰이게 된 import·변수·함수는 지운다.
- 원래 있던 죽은 코드는 요청이 없으면 지우지 않는다.

기준: 바뀐 모든 줄이 오너의 요청(담당은 지시서)으로 바로 이어져야 한다.

## 4. 목표 중심 실행

**성공 기준을 정하고, 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 바꾼다:
- "검증 추가" → "잘못된 입력에 대한 시험을 쓰고 통과시킨다"
- "버그 수정" → "버그를 재현하는 시험을 쓰고 통과시킨다"
- "X 리팩터링" → "전후로 시험이 통과하는지 확인한다"

여러 단계 작업은 짧은 계획을 적는다:
```
1. [단계] → 확인: [점검]
2. [단계] → 확인: [점검]
3. [단계] → 확인: [점검]
```

성공 기준이 분명하면 스스로 반복해 끝낼 수 있다. "되게 해 줘" 같은 약한 기준은 계속 확인을 받아야 한다.

---

**이 지침이 잘 작동하면:** 불필요한 변경이 줄고, 과한 설계로 다시 쓰는 일이 줄며, 실수한 뒤가 아니라 구현 전에 질문이 나온다.
