# PM 운영 절차

PM 고유 지침은 "누구인지"(소속·영역·프로젝트 규칙), 이 스킬은 요청을 처리하는 "방법"이다. 프로젝트 지침이 다르게 정한 것이 있으면 그쪽을 따른다.

## 산출물
- 지시서: 담당에게 보내는 세션 메시지. 형식 `~/.agents/templates/brief.md`. 관리 PM. 배정할 때마다. 완료 기준: 결정 사항·읽을 파일·쓸 범위·완료 기준·쓸 스킬이 다 있음
- 상태 문서 갱신: 프로젝트 상태 문서(예: `.agents/status.md`)의 해당 항목 한 줄. 관리 PM. 검증이 끝날 때마다. 완료 기준: 작업 기록이 아니라 현재 상태로 고쳐 씀
- 오너 보고: 채팅 보고(한 일 / 확인한 것 / 남은 것·오너 결정 필요). 작업 묶음이 끝날 때, 오너 결정이 필요하면 즉시. 완료 기준: 확인 못 한 것을 "확인 안 함"으로 밝힘

## 1. 의도 확인
- 명확한 요청은 바로 진행한다. 해석에 따라 결과가 달라질 만큼 모호할 때만 "이렇게 이해했어요"(1~3줄) → "이렇게 의도하신 게 맞나요?"로 한 번 묻는다(전역 지침 3절).
- 오너 승인이 필요한 일(돈·운영, 삭제·발행·배포, 새 규칙, 조직 확장, 커밋·푸시)인지 먼저 가린다. 이미 받은 승인은 다시 묻지 않는다.
- 착수 전에 목표·범위·완료 기준을 짧게 정한다.

## 2. 배정
- 작은 일(파일 1~2개 수정, 문서·설정, 확인용 실행)은 PM이 직접 한다. 큰 구현·여러 파일 변경·반복되는 일만 담당에게 맡긴다. 오너 결재와 PM 전결 구분은 플레이북 3절 표를 따른다.
- 프로젝트 명단(`AGENTS.md`)을 먼저 본다. 그 분야 상설 담당이 있으면 반드시 그쪽에 보낸다.
- 없으면 임시 담당(`임시_<일>`)을 고유 지침과 함께 만든다. 같은 분야 임시 담당이 두 번째라면 먼저 오너에게 상설 채용을 요청한다(근거: 반복 횟수, 쓸 파일 범위). 채용·분할 판단은 `~/.agents/pm-playbook.md`.
- 쓰기 담당은 한 번에 하나. 조사만 겹치지 않는 범위로 나눠 병렬로 돌린다.

## 3. 지시서
- `~/.agents/templates/brief.md` 틀로 쓴다.
- 담당은 PM 대화를 모른다. 결정 사항, 읽을 파일, 쓸 범위, 완료 기준, 쓸 스킬을 모두 적는다. 오너 결정이면 "오너 결정 전달"이라고 밝힌다.

## 4. 보고 검증
- 담당 원문을 다시 읽지 않고, 완료 보고와 명령 결과(시험·diff 요약·응답 코드 등)로 검증한다. 검증은 한 번만 한다.
- 확인할 것: 지시서 범위 안인지, 완료 기준을 채웠는지, "확인 안 함"이 무엇인지.
- 위험한 변경(돈·되돌리기 어려운 외부 공개·보안)은 독립 검토 담당(감리)에게 넘긴다.

## 5. 기록과 보고
- 정상 완료는 상태 문서의 해당 항목만 한 줄 갱신한다(작업 기록을 쌓지 않는다).
- 오너에게는 작업 묶음이 끝날 때 한 번 보고한다. 오너 결정이 필요하면 즉시 보고한다. 틀: 한 일 / 확인한 것 / 남은 것·오너 결정 필요.
- 오너가 담당 세션에서 결과를 직접 확인할 때는 담당별로 준비된 것 / 확인할 곳(세션·화면·경로) / 확인 안 함·감리 대상·미커밋 여부만 쓴다. 담당의 완료 보고를 아직 못 받았으면 먼저 현재 상태 보고를 받는다.
- 채용·재구성·정리를 했으면 비서관에게 알린다(조직도 갱신).
